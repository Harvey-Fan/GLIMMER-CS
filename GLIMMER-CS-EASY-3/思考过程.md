# 顺序表实现二叉树：思考过程
## 1. 题目

题目要求用**数组**存二叉树，并约定根结点放在下标 1。给出的下标关系是：

 结点 i 的左孩子是 2i
 结点 i 的右孩子是 2i + 1
 反过来，结点 i 的双亲是 i / 2

eg:

```
下标:    1
       /   \
      2     3
     / \   / \
    4   5 6   7
```

第 1 层 1 个位置，第 2 层 2 个，第 3 层 4 个，第 k 层刚好占下标 [2^(k-1), 2^k - 1]。这个结论后面写层序遍历时会直接用上。

ps :还有一个容易忽略的点：**nodes[0] 永远不用**。因为下标从 1 开始，所以数组虽然开了 100 个格子，真正能存结点的下标是 1 到 99

## 2. 为什么结构体里要有 used

顺序存储有个天然的问题：不是满二叉树的时候，数组中间会有空的。比如下面这棵树，eg:此处的6号位置：为空

```
        1
      /   \
     2     3
    / \     \
   4   5     7
```

光靠 data 没法区分"这里存了个 0"和"这里压根没有结点"，所以题目给的 used 字段是必要的。判断一个位置有没有结点，只看 used，不看 data。

## 3. 各函数的设计思路

### 3.1 init_tree：初始化

题目原文是"让二叉树的大小为 MAX_TREE_SIZE，并将其全部节点设置为空，大小为 0"。我的理解是：

- tree->size = MAX_TREE_SIZE
- 每个结点 used = false，**data = 0**

最后那个"大小为 0"我读成了"结点里的数据清零"，因为 size 前面已经明确是 MAX_TREE_SIZE 了，不可能同时又是 0。如果本意不是这样，改起来也就是一行的事。

这里我用循环把 0 到 size-1 全部清一遍，包括没用的 nodes[0]。原因是：局部变量 SeqBiTree tree; 在栈上，里面是随机值，不清理的话 used 可能是任意字节，后面判断会出错。

### 3.2 set_root：创建根

根固定放 nodes[1]。我让它在两种情况下返回 false：

1. tree 是空指针；
2. 根已经存在。

### 3.3 set_left_child / set_right_child：创建孩子

这两个函数几乎一模一样，区别只有孩子下标是 2p 还是 2p + 1。我把公共逻辑抽成了一个内部函数 set_child，两个对外函数只是薄薄的包装，这样校验逻辑只写一遍，不会出现"左边修了 bug 右边忘了"的情况。

校验顺序我是这样排的，每一道都对应一种真实会出错的情形：

| 顺序 | 检查 | 防的是什么 |
|---|---|---|
| 1 | parent_node 在 [1, size-1] 内 | 传了 0、负数、或超出数组的下标，直接访问会越界 |
| 2 | 双亲位置 used == true | 不能给一个不存在的结点挂孩子，否则会产生"悬空"结点 |
| 3 | 孩子下标 < size | 双亲在数组靠后的位置时，2p 可能已经超出数组 |
| 4 | 孩子位置还没被占 | 避免重复创建覆盖已有孩子 |

我专门想过会不会整数溢出：parent_node 经过第 1 步后最大是 99，乘 2 也才 199，远小于 int 的上限，所以可以先算再判断，不用绕路。

### 3.4 level_order：层序遍历

这是我觉得最有意思的一个。普通二叉链表的层序遍历需要一个队列，但顺序存储的数组下标**本身就是层序**，从 1 往后扫一遍就是按层的顺序，不需要队列。

难点只在两件事：

**（a）怎么知道每层从哪到哪？**
利用前面推出的结论：第 k 层是 [2^(k-1), 2^k - 1]。代码里用 start 表示一层的起点，每层结束后 start *= 2 跳到下一层，终点就是 start * 2 - 1。

**（b）打印到哪里停？**
如果老老实实打印整个数组，100 个位置会打出 7 层，后面全是 -1，完全没法看。所以我先从后往前找到**最后一个有结点的下标 last**，然后只打印到 last 所在的那一层为止。外层循环的条件 start <= last 刚好实现这一点：只要这一层的起点不超过 last，这层就一定包含了 last 或者在它前面，要打印；一旦起点超过 last，后面全是空层，直接结束。

另外，每层末尾的 -1 也会打出来（比如 last 在第 3 层的第 1 个位置，那这层剩下的 3 个空位还是要补 -1），这样每一层的宽度始终是 2^(k-1)，看起来是整齐的。

空树我单独处理，打印 (empty tree)，不然会什么都不输出，让人以为程序没跑。

## 5. 复杂度

| 函数 | 时间复杂度 | 说明 |
|---|---|---|
| init_tree | O(MAX_TREE_SIZE) | 要逐个清空 |
| set_root / set_left_child / set_right_child | O(1) | 下标直接算出来，不用找 |
| level_order | O(MAX_TREE_SIZE) | 最坏要扫一遍数组 |

顺序存储的好处就体现在这里：任意结点的孩子、双亲都能 O(1) 算出来，不需要指针。


## 6. 反思：这种存储方式的代价(参考AI)

做完之后我对顺序存储的局限有了更直观的感受：

- **浪费空间**：树越"瘦长"越浪费。极端情况下，一棵只有右孩子的链状树，有 n 个结点却需要 2^n 量级的数组，非常浪费，很快就装不下了。
- **容量固定**：MAX_TREE_SIZE 是编译期写死的，超过就只能返回 false。
- **适合的场景**：完全二叉树或接近完全的树，比如堆
